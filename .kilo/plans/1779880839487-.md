# Site Content CMS — Editable Text Across All Pages

## Summary

Build a system where all ~70+ hardcoded text strings across 6 pages become database-driven and editable from the admin panel. Two editing interfaces share the same underlying data:

1. **Admin "Content Manager" tab** — section-based form view for structured editing
2. **Edit Site Mode** — click any text directly on the live site with hover outlines and inline save

## Recommendation

Build **both**. They share the same DB + API and complement each other. The section view is the safety net (bulk review, search, quick scan). The edit mode is the premium UX (visual context, one-click edits). Implementation order: DB/API first, then section view, then edit mode.

## Phase 1: Database + API

### New D1 Table (`migrations/002_site_content.sql`)

```sql
CREATE TABLE IF NOT EXISTS site_content (
  content_key TEXT PRIMARY KEY,
  content_value TEXT NOT NULL,
  max_chars INTEGER,
  page TEXT NOT NULL,
  section TEXT NOT NULL,
  element_type TEXT NOT NULL DEFAULT 'text'
);
```

**Seed data**: All current hardcoded text inserted with `content_key` following namespace convention:
- `{page}.{section}.{field}` e.g. `about.hero.title`, `founder.bio.list.1`, `contact.channel.email.label`
- `max_chars` derived from CSS constraints (e.g., page titles ≤ 50 chars based on 10ch × ~5px avg)

### API Endpoints

#### `GET /api/site-content`
- Public, no auth
- Returns all `{ content_key, content_value }` pairs as a flat object
- Response: `{ "about.hero.title": "Story first. Always.", ... }`

#### `PUT /api/admin/site-content`
- Admin auth (Bearer token, same as existing admin endpoints)
- Accepts `{ content_key, content_value }` — single field update
- OR accepts `{ updates: [{ content_key, content_value }] }` — bulk update
- Validates `content_value.length <= max_chars`, returns 422 with clear error if exceeded
- Returns updated field on success

### New Cloudflare Function Files
- `functions/api/site-content.js` — GET handler
- `functions/api/admin/site-content.js` — PUT handler

## Phase 2: Frontend Content Layer

### New JS: `js/site-content.js`
- IIFE, loaded on every page (for public pages) or on admin + edit mode
- On public page load:
  1. Fetches `GET /api/site-content`
  2. Queries all `[data-site-key]` elements
  3. Replaces their `textContent` with the DB value for that key
  4. If a key has no DB record, keeps the hardcoded fallback text
- Fallback: on network error, hardcoded text remains visible — site never breaks

### HTML Changes (every page)
Each text element gets a `data-site-key` attribute with the hardcoded text as fallback:

**Before:**
```html
<h1 class="page-title">Story first. Always.</h1>
```

**After:**
```html
<h1 class="page-title" data-site-key="about.hero.title">Story first. Always.</h1>
```

## Phase 4: Edit Site Mode

### Trigger

From admin Content Manager tab, a button: **"[Edit Site Content]"** — opens a new window/tab:

```
/about.html?edit=1
```

This opens the actual public page with an injected edit mode overlay.

### How Edit Mode Works

On page load, `js/site-content.js` checks for `?edit=1` query parameter AND validates the admin token from `localStorage.ss_admin_token` by calling a lightweight auth check (`POST /api/admin/login` with stored token, or a new `GET /api/admin/verify`).

If authenticated:

1. **Top bar injected** at the top of `<body>`:
   ```
   ┌──────────────────────────────────────────────────────┐
   │ [← Back to Admin]  Site Content Editing  [Done Editing]
   └──────────────────────────────────────────────────────┘
   ```
   - `z-index` above all content, sticky
   - Gold/dark theme matching admin
   - "Done Editing" closes the tab/window

2. **Editable zones highlighted**:
   - All `[data-site-key]` elements get a subtle CSS outline:
     - Default: `outline: 1px dashed rgba(184,160,106,0.18)` (barely visible)
     - Hover: `outline: 1px solid rgba(184,160,106,0.7)` with subtle golden glow (`box-shadow`)
     - Click: opens inline editor

3. **Inline editor** (positioned floating popup):
   - Appears right below or above the clicked element
   - Contains: textarea (pre-filled), char counter, Save/Cancel buttons
   - On save: calls `PUT /api/admin/site-content`, updates the element's textContent, closes popup
   - On cancel: closes popup
   - Click-outside or Escape: closes popup
   - Validation: if exceeds max_chars, shows red error in popup, disables Save button

4. **Navigation during edit mode**:
   - Internal links preserve `?edit=1` parameter
   - Transition overlay still plays (site integrity), but after transition the next page also enters edit mode
   - `transition.js` already respects links — we just need to append `?edit=1` to navigation URLs during edit mode

### New CSS: `css/edit-mode.css`
```css
.edit-mode-bar { ... }     /* top bar */
.edit-mode-outline { ... }  /* subtle dashed gold outline */
.edit-mode-hover { ... }    /* brighter on hover */
.edit-mode-popup { ... }    /* floating inline editor */
```

### JS additions to `js/site-content.js`
- Edit mode activation check (query param + auth)
- Top bar injection
- Outline + hover + click handlers on `[data-site-key]`
- Inline popup editor (create, position, handle save/cancel/close)
- `?edit=1` propagation on link clicks during edit mode
- Click-outside and Escape to close popup

### Security Considerations
- Edit mode NEVER activates without valid admin auth
- Token validated on page load via API call
- If token is invalid/expired, edit mode silently fails (page renders normally, `?edit=1` is ignored)
- All write operations require Bearer token (enforced server-side)

## Phase 5: Char Limit Enforcement (Design Frame Protection)

### Deriving `max_chars` values
Each element type has a CSS-defined width constraint. Approximate max chars:

| Element type | CSS constraint | Approx max chars |
|---|---|---|
| `.page-title` | max-width 10ch | 50 chars |
| `.hero-title` | clamp(3.8rem, 8.2vw, 7rem) | 30 chars |
| `.page-lead` | max-width 62ch | 310 chars |
| `.panel h3` | within panel card | 40 chars |
| `.panel p` | within panel (50% of max) | 200 chars |
| `.card h3` | within card column | 30 chars |
| `.card p` | within card column | 150 chars |
| `.hero-film` | single word | 20 chars |
| `.hero-story` | single line | 40 chars |
| `.eyebrow` | small label | 30 chars |
| `.hindi-marker` | single word | 15 chars |
| `.footer left` | single line | 60 chars |
| `.footer-devanagari` | single phrase | 30 chars |
| `.nav a` | nav link text | 15 chars |
| `.progress-head span` | label | 40 chars |
| `.ring span` | phrase | 20 chars |
| `.channel small` | label | 15 chars |
| `.channel a` | URL/label | 50 chars |
| `.quote-block p` | quote text | 250 chars |
| `.preloader-word` | single word | 10 chars |

These approximate values go into the seed data `max_chars` column. They can be tuned manually.

### Validation Flow
1. Client-side: char counter shows `{current}/{max}` in real-time
2. On save: if `value.length > max_chars` → red error: `"Text exceeds design frame. Max XX characters. Current: YY."`, save blocked
3. Server-side: same check, returns HTTP 422 with descriptive error

## Risks / Pitfalls

1. **Transition system interference**: The 2.4s overlay in `transition.js` uses `location.assign`. Edit mode must be re-initialized on each page navigation. Solved by checking for `?edit=1` + auth on every page load.

2. **Content flash**: Before `js/site-content.js` fetches and populates, the hardcoded fallback text will be visible momentarily. This is actually correct behavior — the hardcoded text IS the fallback, so there's no "wrong" content flash, just a brief moment before the DB version replaces it. For edit mode, this is acceptable UX.

3. **`title` and `meta` tags in `<head>`**: These can't have `data-site-key` attributes in the static HTML. Options: (a) Leave them out of the editable system (they're SEO-only, rarely changed), or (b) Use JS post-populate to set `document.title` and create a `<meta name="description">` dynamically. Going with (a) for simplicity — keep meta tags as hardcoded defaults, editable in DB if someone wants to change them, but they won't render dynamically.

4. **Nav text editing**: Nav is identical across all pages. If "Intent" is changed to "About", all pages reflect it. The shared key system handles this — same key on every page, one DB record.

5. **Edit mode + preloader**: On home page with `?edit=1`, the preloader should still play (it's part of the site experience), then edit mode activates after. We skip `sessionStorage.ss_skip_maun` so the preloader always shows. But if the admin is rapidly navigating pages, this gets annoying. We could skip the preloader in edit mode by setting `ss_skip_maun` before navigation.
